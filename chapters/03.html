这一章在做什么

应用里的数据，最后要装进一种通用的形状：表、JSON 文档、顶点和边组成的图、一串不可变的事件，或者数据框和矩阵。这一章把它们摆在一起比，顺带看查它们的语言。主线是数据之间的关系：一对多的树放进文档最顺，多对一、多对多要靠 ID 和连接，关系四通八达时用图。另外两条线：模式由数据库在写入时检查，还是由代码在读取时解释；写的形状和读的形状要不要分开。

读之前：先预测

第 1 章区分了记录系统和派生数据，第 2 章用社交网络的时间线讲了「物化」：预先把查询结果算好，写的时候多干活，读的时候省事。这一章往前退一步，问数据本身该存成什么样子，第 2 章那条时间线会在 §1.2 再出现一次。下一章（第 4 章）讲这些模型在磁盘上怎么实现；第 5 章接着讲模式怎么随时间演化；§3 的事件日志和物化视图，到第 12 章讲流处理时还会接着讲。

一个视频网站给每个用户预先算好「关注动态」，列表里每一条只存视频 ID 和上传者 ID；打开页面时，再按 ID 去查标题、播放量、上传者的昵称和头像，显示最新的 50 条。用户甲关注了 50 个人，用户乙关注了 5000 个人。打开页面时「按 ID 查回内容」这一步，乙的开销大约是甲的多少？

读完了？对照我找到的
  • ORM 的账：N+1 查询，每条记录各发一次查询；好处是少写样板代码，能帮着缓存查询结果、管理模式迁移。
  • 存 ID：写法统一、不歧义、改一处就行、好做多语言、好搜索；变得快的数据（点赞数、头像）只存 ID，读时再查。
  • 星型：查询更好写；数仓里是不再修改的历史记录，没有多份副本要同步的问题。
  • 文档模型：不能直接引用文档里的嵌套项，多对一、多对多要靠引用；可拖动排序的列表直接存成数组就行。
  • GraphQL：不许递归、不许任意搜索条件，因为查询来自不可信的客户端；重复换来的是客户端渲染简单。
  • 事件溯源：外部信息（如汇率）要写进事件或能按时间重查；个人数据难删（GDPR，可用加密粉碎）；重放时别重复触发外部副作用。

先用中文过一遍

关系的形状：一对多放进文档，多对多要靠引用

拿一个菜谱 App 来想。一道菜谱有好几个步骤，每个步骤只属于这道菜：这是一对多，整份数据是一棵树。存成一个 JSON 文档最自然，打开菜谱时一次读出全部内容，不用拼。存进关系数据库，就要拆成菜谱表、步骤表，读的时候再按菜谱 ID 拼回来。

再看作者和食材。很多菜谱是同一个作者写的，这是多对一；一道菜用好几种食材，一种食材出现在很多道菜里，这是多对多。把作者的资料、食材的说明抄进每个菜谱文档，改一处就得改一大片，所以文档里只存它们的 ID，指向别的文档。到这一步，文档模型也离不开「按 ID 去找另一条记录」，也就是连接。关系模型处理多对多的标准做法，是一张关联表：每一行把一个菜谱 ID 和一个食材 ID 连起来，两列各建一个索引，两个方向都能查。

存 ID 还是抄一份：规范化和反规范化

公司内部的工单系统，每张工单要显示负责人的名字。可以只存员工 ID，显示时再按 ID 查名字；也可以把名字直接抄进工单里。前一种叫规范化：给人看的信息只存一处，别处都用一个对人没有意义、所以永远不用改的 ID 去引用。员工改了显示名，改一行就完了，代价是每次读工单都要多查一次（关系数据库里是连接，在应用代码里按 ID 查回来叫「补全」）。后一种叫反规范化：读的时候直接拿到，但改名要改所有副本，漏改一张，数据就前后不一了。

这和第 2 章的物化是一回事：反规范化的副本是派生数据，你得有一套机制在原数据变了以后去更新它们。书里还讲了一种折中：预先算好的列表里只存 ID，读的时候再补全。哪些东西抄、哪些只存 ID，要看它变得多快、读写各有多贵。

图：顶点、边，和不知道要走几步的查询

多对多的关系一多，而且各种东西互相连着，用图更自然：每样东西是一个顶点，每个关系是一条边。属性图模型里，顶点和边都带一个标签（「这是文件夹」「这是编辑过」）和一组键值属性。任何顶点都能连向任何顶点，一张图里可以同时放人、文件、文件夹、标签。

图查询难在路径的长度事先不知道。拿网盘来说：「小周编辑过的文件里，哪些在共享盘『项目资料』下面？」文件可能直接在共享盘里，也可能隔了三层子文件夹。图查询语言可以写「沿着『在……里面』的边走一次或多次」；关系数据库的每走一条边就是一次连接，连接的次数不固定，就得用递归查询（WITH RECURSIVE）：从根开始一轮轮往下展开，直到没有新的为止。

用属性图的查询语言（这里按 Cypher 的写法）大概是这样，*1.. 的意思是这条边走一次或多次：

MATCH (u:User {name: '小周'}) -[:EDITED]-> (f:File)
      -[:IN*1..]-> (:Folder {name: '项目资料'})
RETURN f.name

同一件事，顶点存在 items 表、边存在 links 表，用 SQL 的递归查询写：

WITH RECURSIVE under(id) AS (
    SELECT id FROM items WHERE kind = 'folder' AND name = '项目资料'
  UNION
    SELECT l.src FROM links l JOIN under ON l.dst = under.id
    WHERE l.kind = 'in'
)
SELECT f.name
FROM items f
JOIN under ON f.id = under.id
JOIN links e ON e.dst = f.id AND e.kind = 'edited'
JOIN items u ON u.id = e.src AND u.name = '小周'
WHERE f.kind = 'file';

这两段是本站写的。书里用另一个例子，把同一个查询分别用 Cypher、SQL、SPARQL、Datalog 写了一遍，读的时候留意行数差多少，以及 Datalog 怎么把递归拆成两条规则。

事件溯源：先记下发生了什么，读的样子另外算

前面几种模型，写进去的形状就是读出来的形状。事件溯源把两者拆开：写的时候只往一个日志末尾追加事件，每个事件用过去时说一件已经发生的事（「书已借出」「书已归还」），写进去就不再改、不再删；读的时候不查日志，而是查从日志派生出来的物化视图，每个视图为一类查询优化。这种「写一种表示、读另几种表示」的做法叫 CQRS。

用户的请求先是一个「命令」，校验通过了才变成事件写进日志，所以日志里只有有效的事件，下游的视图不能拒收。视图随时可以删掉，按同样的顺序、用同样的代码把事件重放一遍，就能重新算出来；这要求处理事件的逻辑是确定的，重放时也不能重复做发短信这类对外的动作。

读完：回到你的预测

书里的答案是第二项（§1.2）。列表是预先算好的，打开页面时只需要把这一页的 50 条按 ID 查回来：每条一次查询，彼此独立，可以并行。开销取决于一页显示几条，和你关注了多少人、有多少人关注你都无关。书里拿 X 的时间线说明的正是这一点：读时做连接，并不一定妨碍扩展。只存 ID 的原因也在这一节：点赞数、昵称、头像变得太快，抄进列表要么过时，要么得不停地改写成千上万份副本。想一想：如果不预先算好列表，每次打开页面都现场去查所有关注对象的最新视频，答案会变吗？

书里的答案是第四项（§1.5）。在大多数关系数据库里，加一个带默认值的列很快，大表也一样；慢的是 UPDATE，因为每一行都要重写。书里还给了一个绕开的办法：只加一个默认为 NULL 的列，旧数据等到读的时候再拆，这其实就是文档数据库读时模式的做法，代价是每个读这张表的地方都要处理新旧两种格式。想一想：如果要改的是某一列的数据类型，答案会变吗？

判断题：换成你来选

场景都是本站编的。先选，再看解释；解释里写了对应的节号，拿不准就回原书看那一节。

这份数据存成什么样最省事？§1.5

场景：一个低代码表单平台，每个客户自己定义表单的字段，几千种表单各不相同，客户还会随时加减字段。提交上来的数据几乎总是整份展示、整份导出。

这正是书里说的读时模式占优的情形：对象种类多到没法每种一张表，结构由外部（客户）决定、随时会变。整份读写还能享受文档的局部性。每种一张表要不停地做模式迁移；图模型擅长的是错综的关系，这里没有；预留通用列看着是一张表，其实每列的意思还是要在读的时候按表单去解释，还白白浪费列。

两个方向都要查的共享关系，怎么存？§1.3

场景：网盘里一个文件夹可以共享给很多人，一个人也能收到很多人的共享。「我共享出去的」和「共享给我的」两个页面都要快。现在的设计是在文件夹文档里存一个「共享对象 ID」数组。

多对多关系要双向查，书里的规范化做法是关系只存一处，靠二级索引支持两个方向：关系表的两列各建索引，或者在文档数组里的 ID 上建索引。两边各存一份是反规范化，一边写成功、一边失败，两份就对不上了。全表扫描太慢；把文件夹内容嵌进收件人文档，文件一改就要改所有副本。

层数不固定的物料清单，怎么查？§2.3§2.6

场景：一家设备厂的物料清单：整机由部件组成，部件又由更小的部件组成，层数不固定。数据在 PostgreSQL 里，一张「父部件—子部件—数量」的表。新需求：列出某个型号的整机用到的全部螺丝，不管在第几层。

要走的边数事先不知道，正是书里说的递归公用表表达式的用处：写起来比图查询语言啰嗦，但能在数据库里一次做完。写死 6 次连接，哪天多一层就悄悄漏掉螺丝；GraphQL 故意不支持递归查询；应用里一层层发查询能得到对的结果，但请求次数随部件数增长，是 N+1 问题的放大版。

重建视图之后，历史报表的数字为什么变了？§3

场景：一家连锁咖啡店的会员系统用事件溯源，「订单已支付」事件里只记了消费金额。积分视图处理事件时，去配置服务读当前的「每消费 1 美元积几分」。上个月运营把这个比例从 10 调成了 12。前几天修了积分视图的一个 bug，删掉视图、从头重放事件，结果所有老会员的历史积分都变多了。

书里讲过同一类问题：视图要能从日志可重复地算出来，处理逻辑就必须是确定的。积分比例是事件之外的信息，今天读和去年读不一样。办法是把当时的比例写进事件，或者按事件里的时间戳去查当时生效的比例，保证同一个时间戳永远得到同一个结果。事件不可变，顺序由日志保证；漏掉退款事件只会让个别会员的积分偏多，而且漏的是本该有的扣减，不会让所有人都按同一个比例变多。

分析师嫌查询难写，数仓的模式怎么改？§1.4

场景：一家连锁健身房的数据仓库，事实表一行是一次上课签到。维度又拆成了子维度：门店→城市→大区，课程→课程类别，教练→教练等级。分析师抱怨一条查询要连接七八张表。

现在是雪花模式。书里说星型虽然没那么规范化，但分析师用起来更简单，所以常被优先选择；再往前一步是一张大表，相当于把连接预先算好，多占空间、换更快的查询。数仓里的数据是不再修改的历史记录，反规范化带来的一致性问题在这里不突出。改成每个会员一行的汇总，就丢了「事实按单个事件记录」带来的分析灵活性；图数据库对这种多对一为主的结构没有帮助。

值得停下来的句子

Document databases are sometimes called schemaless, but that’s misleading as the code that reads the data usually assumes some kind of structure— §1.5。本站译：文档数据库有时被称为「无模式」的，但这个说法有误导性：读数据的代码通常都假定了某种结构。

值得停，是因为它把一场常见的争论换了个问法。问题从来不是「要不要模式」，而是模式写在哪里、由谁来保证：写时模式由数据库在写入时把关，读时模式散落在每一段读数据的代码里。书里拿它类比静态类型和动态类型，两边各有拥护者。读到第 5 章的模式演化时，这句话还会派上用场。

You should always be able to delete the materialized views and recompute them by processing the same events in the same order…— §3。本站译：你应该随时可以删掉物化视图，按同样的顺序处理同样的事件，把它们重新算出来……

事件溯源的好处，几乎都从这一条长出来：视图有 bug 就删掉重算，想换个方式展示就再派生一个视图。它的麻烦也都是为了守住这一条：处理逻辑必须确定（不能现取汇率），日志的顺序必须固定，重放时不能再触发对外的动作。第 12 章讲流处理时，会回到事件日志和物化视图这个话题。

检查一下理解

1.（§0）声明式查询语言的好处，为什么不只是「写起来短」？

它把执行细节交给了数据库：用哪个索引、按什么顺序连接、要不要并行，都由查询优化器决定。所以数据库改进了执行方式，查询一个字都不用改。

2.（§1.1）N+1 查询问题是怎么出现的？怎么避免？

用 ORM 先查出 N 条记录，再为每一条各发一次查询去取关联数据，一共 N+1 次，比在数据库里做一次连接慢。办法是告诉 ORM 在取主记录时一并取回关联数据。

3.（§1.2）为什么说用 ID 引用时，ID 本身永远不用改？

ID 对人没有意义，只在数据库内部用。它指向的信息（地名、公司名）可以变，ID 不必跟着变；而对人有意义的东西迟早可能要改，抄了多份就得每份都改。

4.（§1.4）星型模式里，事实表的一行代表什么？维度表回答哪些问题？

一行是某个时刻发生的一个事件，比如一次购买。维度表通过外键挂在事实表上，回答这个事件的谁、什么、在哪、何时、怎样、为什么。日期也常做成维度表，好标出节假日。

5.（§1.5）文档模型适合什么样的数据？它有什么局限？

适合一对多的树、通常整棵一起读的数据。局限是不能直接引用文档里的嵌套项，多对一、多对多要靠引用；文档要整个读、整个重写，所以最好小一点，避免频繁的小更新。

6.（§2.1）图模型里一条边只能连两个顶点。要表示三方的关系怎么办？

为每一个这样的关系建一个额外的顶点，再从它连边到三方各自的顶点；或者用超图。关系表做这件事更直接：一行里放三个外键就行。

7.（§2.6）GraphQL 为什么故意不支持递归查询和任意搜索条件？

它的查询来自用户设备上的客户端，是不可信的来源。允许执行代价很高的查询，用户（哪怕无意）就可能把服务器拖垮，造成拒绝服务。

8.（§3）事件溯源里，命令和事件有什么区别？事件为什么用过去时命名？

命令是用户发来的请求，要先校验，可能被拒绝；校验通过、执行了，才变成事件写进日志，此后就是既成事实，下游不能拒收。过去时表明它记录的是已经发生的事，以后取消也只是追加一个新事件。

用一句话说这一章（写给一个没读过的朋友）：

精彩回顾

一句话：选数据模型，先看数据之间的关系长什么样：树用文档，多对多靠引用和连接，四通八达用图；写和读的形状不同，就把它们拆开。

「无模式」其实有模式

文档数据库不检查结构，但读数据的代码一定假定了结构。区别只在模式写在哪儿：写入时由数据库把关，还是读取时由代码解释。

§1.5
关注一万人也不怕补全

预先算好的列表只存 ID，读时按 ID 查回内容。这一步的开销只和一页显示几条有关，还能并行。

§1.2
四行对三十一行

同一个「沿着边走任意多步」的查询，书里的 Cypher 写了 4 行，SQL 的递归查询写了 31 行。模型和语言选得对不对，差别就这么大。

§2.3
事件用过去时

事件记的是已经发生的事，写下就不改；后来取消了，也只是再追加一条。视图随时可以删掉，重放日志再算一遍。

§3
GraphQL 故意不让你递归

查询来自不可信的客户端，所以不许递归、不许任意条件搜索。名字里有 graph，底下可以是任何数据库。

§2.6
拖来拖去的待办列表

用户自己排顺序的列表，文档里存成一个数组就完事；关系数据库没有标准做法，只能靠整数排序列、链表或分数索引这类技巧。

§1.5
Codd 早就允许嵌套

关系模型最初的描述里，一个值可以是一张嵌套的表。三十多年后 SQL 加上 JSON 和 XML，算是绕回来了。
