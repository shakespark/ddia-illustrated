这一章在做什么

进程会崩，网络会断，几个客户端会同时改同一份数据。事务把一组读写打成一个包：要么全部生效，要么全部撤销，出了错应用重试就行。这一章的大头是隔离：为了性能，数据库常用读已提交、快照隔离这类弱隔离，各挡住一部分竞争，丢失更新和写偏斜却可能漏过去；真正的可串行化有串行执行、两阶段锁、SSI 三种做法，代价各不相同。最后讲跨多个节点时怎样用两阶段提交让大家一起提交，以及它在出故障时的麻烦。

先用中文过一遍

读已提交和快照隔离：读到的是哪个版本

隔离要解决的是：几个事务同时跑，彼此别踩到对方。最弱的一档实用级别是读已提交，它保证两件事：只读得到别人已经提交的数据（不脏读），只覆盖别人已经提交的数据（不脏写）。不脏写靠行锁：要改一行先拿锁，拿到提交或中止才放。不脏读通常不用锁，而是让数据库同时记着这一行的旧值（已提交的）和新值（还没提交的），别的事务来读，就给它旧值。

读已提交挡不住一种情况：一个事务先后读两行，两次之间别人改了这两行并提交了，它看到的是一半旧、一半新。只读一下，过几秒刷新就好；可要是备份或对账这种要跑几个小时的读，就会读出一个从来没存在过的状态。快照隔离的办法是把「旧值和新值」推广成「好几个已提交的版本」：每个版本标着是哪个事务创建的、哪个事务删除的（更新就是删一个旧版本、加一个新版本）。事务开始时记下当时还有哪些事务没提交，之后读任何一行，都只挑「开始那一刻已经提交」的那个版本。这就是多版本并发控制（MVCC）。读的人不挡写的人，写的人也不挡读的人。

两个事务同时写：丢失更新和写偏斜

前面两级主要管「读的人看到什么」。两个事务都要写时，问题更多。最常见的是丢失更新：两个事务都先读一个值、在程序里改、再整个写回去，后写的那个把先写的冲掉了。读已提交挡不住它：后一次写发生在前一个事务提交之后，算不上脏写。对策有好几种：让数据库做原子的「在原值上加减」，显式给要改的行加锁，让数据库自动检测并中止后写的那个，或者用「值没变才写」的条件写。

写偏斜更隐蔽：两个事务读的是同一批数据，改的却是不同的行。每个事务都先查一个条件（「还有空位吗」），按结果决定写入，而它的写入恰好让对方的条件不再成立。因为两人改的不是同一行，行锁、丢失更新检测统统看不到冲突。更麻烦的是，如果条件查的是「没有符合条件的行」，就连一行可以加锁的东西都没有，这就是幻读引起的写偏斜。

要全挡住：可串行化的三种做法

可串行化的意思是：不管事务实际上怎么交错执行，结果都和某个「一个接一个跑」的顺序一样。这样只要每个事务单独跑是对的，一起跑也是对的。书里讲了三种实现。第一种最直接：真的只用一个线程，一次跑一个事务。前提是事务都很短、数据都在内存里，而且事务要写成存储过程整个交给数据库，不能和应用来回聊。第二种是两阶段锁：读要拿共享锁，写要拿排他锁，读写互相等，拿到的锁一直留到事务结束；为了挡住幻读，还要锁住「查询条件」或者索引上的一段范围。第三种是可串行化快照隔离（SSI）：照快照隔离那样放手让事务跑，只是暗中记下谁读了什么、谁写了什么，到提交时检查自己当初读到的前提有没有被别人改掉，改掉了就中止。前两种是悲观的，有风险就等；第三种是乐观的，先做，出了问题再撤。

跨节点提交：两阶段提交的两次承诺

单机上，「提交」落在一个确定的时刻：提交记录写进磁盘上的日志的那一刻。事务涉及好几个节点时，不能简单地给每个节点发一句「提交」：有的节点可能提交了，有的因为冲突、超时或崩溃回滚了，而已经提交的数据别人可能已经读走，收不回来。两阶段提交加了一个协调者，把提交拆成两轮。第一轮问每个参与者「你能提交吗」，参与者答「是」之前，要先把数据写盘、查过约束，答了就不能反悔。第二轮，协调者收齐答复，把决定写进自己的日志，然后通知所有人。这个决定一旦写下，就要不停重试直到人人照办。代价也在这里：参与者答了「是」之后，如果协调者崩溃，它既不能自己提交，也不能自己回滚，只能拿着锁等。

读完：回到你的预测

答案是第三项（§2.4）：两个都成功，31 人。这正是写偏斜：两个事务读的是同一组行，各自插入的却是不同的新行。丢失更新检测只管「同一行被两个事务改了」，这里没有同一行；行锁也锁不到还不存在的行；快照隔离下谁也看不到对方没提交的插入，所以不会读到 30。书里说，PostgreSQL 的 repeatable read、MySQL 的 repeatable read、Oracle 的 serializable、SQL Server 的快照隔离都不会自动检测写偏斜，要挡住它需要真正的可串行化（§3）。想一想：如果把「已选人数」存成课程表上的一个计数字段，两个事务都去改它，答案会变吗？

答案是第四项（§4.1）。库存库答了「是」，就交出了单方面中止的权利；它又不知道协调者的决定，自己提交也不安全，因为可能有别的参与者投了反对。问订单库听起来可行，但那不是两阶段提交协议的一部分。它只能等协调者恢复、从日志里读出决定再通知它，这段时间里这笔事务改过的行一直锁着（§4.2 讲了这为什么会把系统的其他部分也卡住）。想一想：如果协调者自己用共识算法复制成几台、一台坏了另一台接手（§4.3，第 10 章），库存库还要等多久？

判断题：换成你来选

场景都是本站编的。先选，再看解释；解释里写了对应的节号，拿不准就回原书看那一节。

积分少加了一次，最省事的修法是？§2.3

场景：会员积分服务用 PostgreSQL 的默认隔离级别（读已提交）。代码通过 ORM 先把用户记录查出来，在程序里给积分加上这次的奖励，再整条保存回去。大促期间偶尔有用户反映同一时刻的两笔奖励只到账一笔，日志里没有任何报错。

这是丢失更新：两个读-改-写循环交错，后写的冲掉了先写的。读已提交不防它，因为后一次写发生在前一个事务提交之后。原子更新让数据库自己在原值上加，是书里说的首选；显式加锁（SELECT FOR UPDATE）也行。读未提交只能降低概率，挡不住；缓存与此无关；这里根本没有报错，重试无从谈起。

同一个用户领到两张首单券，加哪一样最划算？§2.4

场景：新用户可以领一张首单券，每人限一张。领券接口在一个事务里先查「这个用户领过没有」，没领过就插入一条领券记录。数据库用快照隔离。日志显示偶尔有人领到两张，都是用户连点了两下。

这是幻读造成的写偏斜：两个事务都查到「没有」，各插入一条。查的是不存在的行，SELECT FOR UPDATE 没东西可锁；两条插入是不同的行，丢失更新检测也看不见。唯一约束让第二条插入直接失败，简单可靠。前端置灰挡不住重放的请求，书里提醒过攻击者会故意并发地打你的接口。

对账一跑，下单就超时。保留可串行化，该怎么改？§3.2§3.3

场景：订单库用两阶段锁实现可串行化。每晚的对账任务要在一个事务里扫一遍整张订单表，跑 40 分钟；这 40 分钟里，下单接口大面积超时。

两阶段锁下，读整张表要拿整张表的共享锁，在它提交之前所有写都得等。SSI 里读不挡写、写不挡读，只读事务在快照上跑，不用拿锁，书里说长时间的只读事务在 SSI 下没问题。连接池大了也只是更多人排队；拆成并行扫描照样要拿共享锁；真串行执行下这 40 分钟的事务会让所有事务都停下。

消息重投导致商家余额加了两次。最稳妥的修法是？§4.2§4.4

场景：支付成功的消息从消息队列进来，消费者在数据库里给商家余额加钱，提交后向队列确认。偶尔消费者在提交之后、确认之前崩溃，队列把消息重投一次，钱就加了两次。有人提议上 XA，把消息确认和数据库写放进同一个两阶段提交。

书里 §4.4 的做法：只用数据库自己的事务，把消息 ID 和业务写一起提交，处理就变成幂等的，重投也只生效一次。XA 理论上可行，但要求两边都支持，协调者一出问题，存疑的事务就一直持锁，书里花了整整一节讲这些麻烦。先确认再处理，崩溃时会丢消息；调超时与崩溃无关。

用单线程串行执行，最先出问题的会是哪里？§3.1

场景：一个抢购系统想用「单线程一次跑一个事务」换取可串行化：热数据全在内存，下单事务写成存储过程，平均 50 微秒跑完。运营后台还有一个「导出全部订单」的功能，也作为一个事务在这个线程上跑，要 3 秒。

串行执行要求每个事务都又小又快，一个慢事务就能让整条流水线停下。书里的办法是让只读的长查询在快照上跑，放到串行执行的循环之外。存储过程难管理是真问题，但不是最先爆的；题目说了热数据在内存里；只有一个线程，谈不上死锁。

值得停下来的句子

Transactions are not a law of nature; they were created with a purpose—namely, to simplify the programming model for applications accessing a database.— §0。本站译：事务不是自然规律；它是带着目的被造出来的，那就是让访问数据库的应用编程起来更简单。

这句话定下了全章的读法。既然事务是为了简化编程而存在，评价一个隔离级别、一个提交协议，就要问它替应用挡掉了哪些情况、还剩哪些要应用自己操心。后面讲弱隔离时作者一再抱怨，正是因为它们把一部分复杂度又推回给了应用，而且推得不明不白。

the database guarantees that if the transactions behave correctly when run individually, they continue to do so when run concurrently— §3。本站译：数据库保证，如果事务单独运行时行为正确，那么并发运行时也依然正确。

这是可串行化最有用的一种说法。它把「并发对不对」这个难问题，换成了「单个事务对不对」这个容易的问题，应用开发者只需要想后者。弱隔离级别给不了这句保证，所以每用一个弱隔离级别，你都得回到 §2 那几种竞争，一个一个排查自己的代码。

检查一下理解

1.（§1.1）作者为什么说「可中止性」比「原子性」更贴切？

ACID 的 A 讲的不是并发时别人看不到半成品，那是 I 的事。它讲的是出错时把事务已经做的写全部丢掉，应用因此可以放心重试。

2.（§1.2）重试一个被中止的事务，什么情况下反而坏事？

事务其实已提交、只是确认在网络上丢了，重试会做两遍；错误来自过载或高竞争时，重试让情况更糟；违反约束这类永久错误，重试没用；发邮件这种数据库之外的副作用会重复发生。

3.（§2.1）防脏读，大多数数据库为什么不让读去拿锁？

一个长时间的写事务会让所有读它那几行的请求一起等，只读请求的响应时间被拖垮，一处慢还会连累别处。所以数据库记下旧的已提交值，写事务提交之前，别人读到的都是旧值。

4.（§2.2）备份和完整性检查为什么特别需要快照隔离？

它们要读很大一片数据、跑很久，期间写入照常进行。没有一致的快照，读到的是不同时刻的拼凑；备份恢复后，这种不一致（比如钱凭空少了）就永久留下了。

5.（§2.3）PostgreSQL 和 MySQL 的 repeatable read 在丢失更新上有什么不同？

PostgreSQL 会自动发现丢失更新，中止后写的那个事务；MySQL 的 InnoDB 不检测。所以有作者认为，按「必须防住丢失更新」的定义，MySQL 提供的不算快照隔离。

6.（§2.4）什么是「把冲突物化」？作者为什么只把它当最后的手段？

幻读的问题是没有行可锁，那就人为造一张表，比如把每个资源、每个时间段预先建成一行，事务先锁住相应的行再检查和写入。但怎么物化很难想对、容易出错，而且让并发控制的细节漏进了业务数据模型，能用可串行化就用可串行化。

7.（§3.1）单线程串行执行为什么要求事务写成存储过程？

交互式事务的大部分时间花在应用和数据库之间来回传语句上，单线程干等就太慢了。把整段事务代码事先交给数据库，数据又都在内存里，它就能不等网络和磁盘一口气跑完。

8.（§4.4）不用跨系统的分布式事务，怎样做到每条消息恰好处理一次？

在数据库事务里先记下消息 ID，再做业务写，一起提交，之后才向消息代理确认。重投时看到 ID 已在库里，就直接确认丢弃；ID 表上的唯一约束挡住两个并发的重复处理。

用一句话说这一章（写给一个没读过的朋友）：

精彩回顾

一句话：事务把一大类故障和并发问题变成「中止，再试一次」；隔离级别越弱，留给应用自己防的竞争越多。

原子性其实是可中止性

ACID 的 A 不管并发，管的是出错时把已做的写全部撤销。这样应用才敢放心重试。

§1.1
C 是应用的事

一致性指应用定义的不变式。数据库只能检查你声明成约束的那部分，其余靠你把事务写对。

§1.1
一行存好几个版本

快照隔离靠多版本：每个版本标着谁建的、谁删的，读的人按开始那一刻挑版本。读不挡写，写不挡读。

§2.2
同一个名字，好几种意思

repeatable read 在 PostgreSQL 里是快照隔离，在 MySQL 里更弱，在 Db2 里是可串行化。看文档，别看名字。

§2.2
前提变了

写偏斜：两个事务各自查条件、各自写不同的行，写完后对方的前提都不成立了。只有可串行化能自动挡住。

§2.4
悲观地等，乐观地查

两阶段锁有风险就等，一个慢事务能卡住一片；SSI 先放行，提交时发现前提过时再中止，只读查询在快照上跑，不用拿锁。

§3.3
答了「是」就不能反悔

两阶段提交靠两次承诺成立；协调者崩溃时，答过「是」的参与者只能持锁干等。

§4.1
启发式，是委婉说法

XA 的「启发式决定」让参与者自己拍板，作者直说：这多半意味着破坏原子性，只留给灾难时用。

§4.2
